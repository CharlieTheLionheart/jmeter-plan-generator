# F-17: kwdb silently drops `setString` value for the first VARCHAR regular TAG when the preceding SMALLINT column was bound with `setLong`

## Summary

In a time-series table with **2+ regular TAGs** where one TAG is `varchar` and another is `smallint` (or any int family), binding the smallint column with `PreparedStatement.setLong(...)` and then binding the varchar TAG with `PreparedStatement.setString(...)` causes the varchar TAG value to be **silently dropped to empty string** on `kwdb/kwdb:latest`, or **crash the server** (segfault in `MMapTagColumnTable::push_back`) on `kwdb-x86_64-master-dbg:latest` on container restart.

The bug is **not** in the fixture, the JMX, or the JDBC driver class loading. The `setString` call is invoked with the correct value; the server simply ignores it. No exception, no warning.

## Schema (minimal trigger)

```sql
CREATE TS DATABASE f17_repro;
USE f17_repro;

CREATE TABLE t_2rtag (
  ts TIMESTAMP NOT NULL,
  c1 INT                                -- 1+ data columns
) TAGS (
  ptag_varchar_1   VARCHAR(32) NOT NULL,  -- 1 ptag (PRIMARY TAGS)
  rtag_varchar_1   VARCHAR(64) NOT NULL,  -- 1st rtag (varchar) — **this is the one that breaks**
  rtag_smallint_1  SMALLINT    NOT NULL   -- 2nd rtag (smallint)
) PRIMARY TAGS (ptag_varchar_1);
```

## Critical sub-finding: `setShort` works, `setLong` breaks

The bug only triggers when the smallint TAG is bound via `setLong`. The same column bound via `setShort` works correctly:

| Bind for SMALLINT column | `rtag_varchar_1` in DB |
| --- | --- |
| `setLong(idx, value)` (JMX default path) | `""` for all rows |
| `setShort(idx, (short) value)` (alternate) | `op_group_1..4` populated correctly |

The kwdb server seems to remember the JDBC type of the prior bind, and a `setLong` on a `SMALLINT` column type ends up "consuming" or poisoning the next `setString` for the following varchar column.

## Workarounds (verified)

1. **Bind smallint with `setShort` instead of `setLong`** — bypasses the bug. Requires changing the JMX bind loop or wrapping the call site.
2. **Don't add a varchar regular TAG** to time-series tables that also have a smallint/int regular TAG. Use the smallint TAG only, or move the string semantics into a data column.

Neither workaround is acceptable for production: real shig-style data has 2 rtags (`op_group` varchar + `workshop_id` smallint FK). The `op_group` semantics are lost.

## Impact

- **shig smoke test (`tests/kwjdbc_svt/fixtures/test_model_shig.yaml`)** generates a JMX with `t_electmeter` containing 2 rtags. The smoke test reports `0 errors` and `3900 rows` written — but `rtag_varchar_1` is silently `""` for all 3900 rows. The data is **visibly fine** (row counts match) but **semantically wrong** (no rtag partition, queries that filter by `rtag_varchar_1` return empty result sets).
- **KaiwuDB server stability** — on the master-dbg build, a single `t_electmeter` insert with 2 rtags corrupts the ts_db tag table, causing the next server restart to segfault inside `MMapTagColumnTable::push_back` during WAL replay.
- **CI signal** — the smoke cannot detect this bug via the standard 0-error / row-count check. The only way to detect is to query the actual `rtag_varchar_1` content and assert non-empty.

## Recommended fix (kwdb server)

The driver is sending the correct `setString(52, "op_group_3")` call. The server is binding this placeholder to the **SMALLINT column** (not VARCHAR) because of a prior `setLong` that left the column type cached. Resetting the column-type cache between parameter binds, or honouring the JDBC `parameterType` hint from `getParameterMetaData()` (which already reports `varchar` for param 52), should resolve the issue.
