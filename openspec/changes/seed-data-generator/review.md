# Quality Review

## 1. Boundary Conditions
**Status**: ✅ Pass
**Findings**:
- 设计文档中已识别正则生成库可能不支持完整正则语法的风险，并说明当前仅支持 `[一-鿿a-zA-Z0-9-_]` 字符集，但未明确界定不支持的语法子集范围，可能导致用户误用。
- `val_range` 区间表达式（如 `>=`、`<=`、`[min,max]`、`(min,max)`）的边界值处理未在设计中显式讨论，例如整数闭区间是否包含边界、浮点数开区间精度控制等。
- 枚举值数量远小于 `seed_num` 时，设计文档将其标记为预期行为，但未定义 "远小于" 的阈值，也未说明是否需要在配置校验阶段给出警告。
- NULL 值生成策略中，`null_rate` 与 `seed_num` 的乘积非整数时（如 `seed_num=10, null_rate=0.3`），未明确取整规则（向上/向下/四舍五入）。
- 行种子总集以最大 `seed_num` 为行数，但当某列 `seed_num=0` 时，循环填充逻辑是否会导致除零或空列问题，设计未覆盖。
- 字符串正则生成可能产生包含换行符的值，与列种子文件"一行一个值"的纯文本格式冲突，属于潜在的数据边界问题。

**Resolved**:
- 模块 docstring 明确使用 `rstr` 生成正则，不支持反向引用、嵌套量词等高级特性。
- 整数闭区间包含边界，开区间排除端点并调整到最近合法整数；浮点数保留 2 位小数，开区间做防越界修正。
- `null_rate * seed_num` 统一使用 `floor`，NULL 数量不超过比例。
- `seed_num <= 0` 直接抛错；CSV 格式由 Python `csv` 模块自动处理换行符和特殊字符。

**Recommendations**:
- 在模块文档中明确列出正则表达式支持的完整语法子集和明确不支持的语法（如量词嵌套、反向引用等）。
- 补充 `val_range` 边界值处理的精确规则（整数闭区间包含边界、浮点数精度控制位数）。
- 定义 `null_rate * seed_num` 非整数时的取整规则（建议向下取整，保证 NULL 数量不超过比例）。
- 增加 `seed_num=0` 或负数时的防御性处理，明确是报错还是跳过该列。
- ~~为字符串种子值制定换行符转义策略或改用 JSON Lines 格式，避免列种子文件解析歧义。~~
  - ✅ **已解决**: 统一采用 CSV 格式，Python `csv` 模块自动处理

**Open Questions**:
1. ~~字符串种子值的换行符处理：当 `val_range` 为正则表达式时，生成的字符串种子值可能包含换行符。种子文件当前采用"一行一个值"的纯文本格式，是否需要对换行符进行转义，或采用 JSON Lines 等可安全承载任意字符串的格式？~~
   - ✅ **已解决**: 统一使用 CSV 格式（列种子文件和行种子总集均采用 CSV），Python `csv` 模块自动处理字段内的换行符、逗号等特殊字符，无需手动转义
   - 已更新 design.md，新增"列种子文件格式"章节

## 2. Rollback Plan
**Status**: ✅ Pass
**Findings**:
- 设计文档的 Migration Plan 明确指出"无需迁移。这是一个新功能模块。"，说明该模块为纯新增，无存量数据或配置需要回滚处理。
- 种子数据生成产物为文件（列种子文件和行种子总集），不直接修改数据库状态，回滚只需删除生成的文件即可。
- 模块依赖 config-parser 和 ddl-generator，但均为读取依赖，不产生写副作用，回滚时无需协调下游状态。
- 无配置变更、无 schema 变更、无共享状态持久化，回滚复杂度极低。

**Recommendations**:
- 在实现阶段确保生成目录（`seeds/{table}/`）的清理脚本与生成脚本配套提供，便于一键回滚。
- 建议在生成流程中记录生成日志（包括输入配置 hash 和输出文件列表），以便在需要时精确追溯和清理产物。

## 3. Test Coverage
**Status**: ✅ Pass
**Findings**:
- 规格书（spec.md）已覆盖整数/浮点/字符串/枚举/NULL/外键引用/列种子文件/行种子总集等核心场景，场景定义较为完整。
- 但规格书中未覆盖以下测试场景：
  - 边界值测试：`val_range` 取到区间边界时的值生成（如 `[1,1]`、`>=0` 与 `<=0` 交集）。
  - 异常输入测试：非法 `val_range` 格式、非法 `null_rate`（如 >1 或负数）、`seed_num` 为 0 或负数。
  - 并发测试：多表同时生成种子数据时的文件系统冲突。
  - 大容量测试：`seed_num` 极大（如百万级）时的内存和性能表现。
  - 外键引用测试：被引用表 `seed_num` 小于引用表时的采样行为，以及跨库引用的端到端验证。
- 规格书中未定义测试框架或测试策略（单元测试、集成测试、property-based testing）。

**Resolved**:
- 新增 `tests/seed_data_generator/` 覆盖 adapter、generators、reference、io、orchestrator、benchmark。
- 边界值测试覆盖 `[1,1]`、`>=0`、开区间等；异常输入覆盖非法 `null_rate` 和 `seed_num <= 0`。
- 使用 Hypothesis 对整数闭区间和 NULL 比例做 property-based 测试。
- 跨库外键引用、采样替换/循环、缺失 `.ref` 文件均覆盖。
- 并发与百万级性能测试作为 `@pytest.mark.slow` 提供。

**Recommendations**:
- 补充边界值和异常输入的测试场景到规格书，确保模块对非法输入有明确的错误行为定义。
- 增加大容量 `seed_num` 的性能基准测试，验证内存占用和生成耗时是否在可接受范围内。
- 明确测试策略：数值/字符串生成逻辑建议用 property-based testing（如 Hypothesis）验证分布和边界；文件输出建议用临时目录隔离的集成测试。
- 外键引用采样需增加被引用列种子数据为空或不存在时的错误处理测试。

## 4. Backward Compatibility
**Status**: ✅ Pass
**Findings**:
- 该模块为纯新增能力，无现有接口、配置项或数据格式的变更。
- 列种子文件命名约定（`{列序号}_{列名}.{类型名}`）为全新约定，不与现有文件冲突。
- 行种子总集输出格式为内部使用（JMeter 共享内存加载），无外部消费者。
- 依赖的 config-parser 和 ddl-generator 模块的输出接口未因本模块而改变。
- 设计文档的 Non-Goals 中明确排除了自定义数据分布、数据关联生成、种子数据增量更新，这些限制避免了未来兼容性承诺的过度扩张。

**Recommendations**:
- 列种子文件命名约定一旦确定，后续变更将影响 JMeter 采样脚本的文件查找逻辑，建议将其作为稳定接口文档化，避免后续重命名导致兼容性问题。
- 行种子总集格式（嵌套列表/字典）若后续变更，需同步更新 JMeter SetupThreadGroup 的加载逻辑，建议在格式中增加版本标识字段，便于未来扩展。

## 5. Task Granularity
**Status**: ✅ Pass
**Findings**:
- 设计文档仅包含高层决策（数值生成、字符串生成、NULL 策略、行总集格式、外键采样时机），缺乏可执行的任务拆分。没有明确的子模块划分、接口定义或实现顺序。
- 外键引用采样被标记为"在所有表主键种子数据生成完成后"进行，但未说明多表场景下的调度机制（串行还是并行？按拓扑排序还是按配置顺序？）。
- 行种子总集"循环填充较短的列"这一核心算法未细化：循环填充的单位是值还是行？当列类型为 NULL 值时，循环填充是否保持 NULL 位置不变？
- 缺少接口契约：种子数据生成模块的输入（config-parser 输出结构）和输出（文件路径、内存数据结构）的精确类型定义未给出。
- 未明确各类型（int8/int16/int32/int64/float4/float8/varchar/timestamp 等）的生成实现是否统一抽象还是分别实现，这直接影响任务拆分粒度。
- 设计文档中的 Open Questions 中有 4 个未解决问题，其中 2 个（行总集输出格式、外键引用采样机制）属于核心实现细节，应在编码前明确，否则任务无法准确估算。

**Resolved**:
- `tasks.md` 已拆分为 10 组共 55 项可执行任务，覆盖接口、适配器、生成器、外键、文件 IO、行总集、E2E、验证等。
- 实现接口为 `generate_seeds(model, output_dir, seed=None)`，返回 `{db.table: [paths]}`。
- 外键引用无需拓扑排序：仅时序表引用关系表主键，预生成 `.ref` 文件后直接采样。
- 行总集以最大 `seed_num` 为行数，对每列按索引循环取值；NULL 值已写入列种子文件，循环时保持位置不变。

**Recommendations**:
- 将模块拆分为至少 5 个独立任务：① val_range 解析适配层；② 数值类型生成器；③ 字符串/枚举/NULL 生成器；④ 列种子文件输出；⑤ 行种子总集拼接与输出；⑥ 外键引用采样与拓扑排序。每个任务应包含输入、输出、验收标准和预估工时。
- 明确外键引用的多表调度算法（建议采用 Kahn 拓扑排序），并在任务拆分中单独列为一个任务。
- 定义模块对外接口契约（Python 函数签名或类接口），包括输入的列配置结构和输出的文件路径列表、行总集数据结构。
- 在编码前必须解决行总集输出格式（JSON/Python 对象）和换行符转义策略，否则文件输出任务无法开始。
- 为各数据类型（int/float/string/enum/timestamp）分别定义生成函数签名和单元测试任务，避免"一个大任务实现所有类型"的模糊拆分。

**Open Questions**:
1. ~~外键引用跨库引用：是否需要支持跨库引用？当前规格书示例中有此需求。~~
   - ✅ **已解决**: 规格书已明确支持 `ref:库名.表名.列名` 格式的跨库引用
2. ~~行种子总集输出格式：输出为 JSON、Python pickle 还是其他格式？~~
   - ✅ **已解决**: 采用 CSV 格式，文件命名为 `{库名.表名}.csv`，使用 Python `csv` 模块加载
3. ~~`ref` 外键引用的具体采样机制：被引用列的种子如何缓存和复用？是否需要通过拓扑排序（如 Kahn 算法）确定生成顺序？引用列采样时是采用有放回随机抽样还是直接共享被引用列的列表引用？当本表 `seed_num` 大于被引用表时，如何保证引用列行数不受限？~~
   - ✅ **已解决**: 采用预生成主键列种子文件策略
     - 业务约束：只做时序表引用关系表主键，不存在循环依赖
     - 实现方式：预生成被引用的关系表主键列种子文件（`.ref` 文件），时序表tag列和查询参数都从该文件采样
     - 当本表 `seed_num` 大于被引用表时：循环使用被引用表主键列种子文件中的值
     - 已更新 design.md，新增"外键引用采样机制"章节

## Overall Assessment
该模块作为新增功能，在回滚和向后兼容方面风险较低，但任务粒度控制不足是当前最大的实施风险。设计文档停留在架构决策层面，缺少可直接指导编码的接口定义、任务拆分和算法细节。特别是行总集输出格式、外键引用采样机制、换行符处理等 4 个未决问题（已分类迁移至对应维度）若不在开发前解决，将导致实现阶段反复返工。建议优先补齐任务级拆分和接口契约，将 Open Questions 转化为决策后更新设计文档，再进入编码阶段。测试覆盖方面需补充边界值和异常场景，避免交付后因输入校验不足产生缺陷。
