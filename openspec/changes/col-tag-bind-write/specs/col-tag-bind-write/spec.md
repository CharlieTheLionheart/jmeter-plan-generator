## ADDED Requirements

### Requirement: Per-table col_tag_bind_mode sub-mode

The system SHALL support a `col_tag_bind_mode` boolean sub-mode per `write_config` table entry that writes only a ptag-bound subset of data columns per INSERT.

#### Scenario: Default behavior unchanged
- **WHEN** `col_tag_bind_mode` is unset or `false` for a table
- **THEN** the system SHALL fall back to existing full-row INSERT path
- **THEN** no SetupTG column-seed sampler SHALL be added for that table

#### Scenario: Enable with valid configuration
- **WHEN** `col_tag_bind_mode=true` AND `col_num_per_tag=N` AND `N > 0` AND `N ≤ data_col_count` AND `primary_tag_count ≥ 1`
- **THEN** the system SHALL generate Write TG with ptag-bound column subset INSERT
- **THEN** the system SHALL apply to all 5 modes (`single_insert` / `batch_insert` / `single_prepared` / `batch_prepared` / `schemaless`)

### Requirement: Reject invalid col_tag_bind_mode configuration

The system SHALL reject invalid `col_tag_bind_mode` configurations at config-parse time.

#### Scenario: col_tag_bind_mode requires positive col_num_per_tag
- **WHEN** `col_tag_bind_mode=true` AND `col_num_per_tag ≤ 0`
- **THEN** the system SHALL raise a `ValueError` with message referencing `col_num_per_tag`

#### Scenario: col_tag_bind_mode requires at least one primary tag
- **WHEN** `col_tag_bind_mode=true` AND `primary_tag_count=0`
- **THEN** the system SHALL raise a `ValueError` with message referencing ptag requirement

#### Scenario: col_num_per_tag cannot exceed data_col_count
- **WHEN** `col_tag_bind_mode=true` AND `col_num_per_tag > data_col_count`
- **THEN** the system SHALL raise a `ValueError` with message referencing the column count limit

### Requirement: Orchestrator skips row seed file generation under col_tag_bind_mode

The system SHALL skip row seed file generation for tables with `col_tag_bind_mode=true`, while column seed files are generated regardless.

#### Scenario: Skip row seed file generation
- **WHEN** Orchestrator processes a table with `col_tag_bind_mode=true`
- **THEN** the Orchestrator SHALL NOT generate a row seed file for that table
- **THEN** the Orchestrator SHALL still generate column seed files per data_col (existing behavior)

#### Scenario: Existing column seed file generation unchanged
- **WHEN** Orchestrator processes any table (regardless of `col_tag_bind_mode`)
- **THEN** column seed files SHALL be generated by `write_column_seed` (existing API)
- **THEN** column seed file naming SHALL follow `{col_name}.{type}.csv` pattern

### Requirement: SetupTG sampler OR relation

The system SHALL support mixed (OR) mode in SetupTG: existing row-seed sampler + optional appended column-seed sampler.

#### Scenario: All tables in full-row mode
- **WHEN** no table in `write_config` has `col_tag_bind_mode=true`
- **THEN** the SetupTG SHALL emit only the existing row-seed sampler (one per table)
- **THEN** no column-seed sampler SHALL be appended

#### Scenario: At least one table in column-bind mode
- **WHEN** at least one table in `write_config` has `col_tag_bind_mode=true`
- **THEN** the SetupTG SHALL retain the existing row-seed sampler for tables in full-row mode
- **THEN** the SetupTG SHALL append a new JSR223 Sampler responsible for column-seed loading + hash-based row initialization

#### Scenario: Existing row-seed sampler skips tables in column-bind mode
- **WHEN** the SetupTG row-seed sampler iterates tables
- **THEN** for tables with `col_tag_bind_mode=true`, the sampler SHALL skip row seed file loading
- **THEN** the sampler SHALL continue iterating tables in full-row mode

### Requirement: Column seed sampler writes to bind-namespaced SharedMemory

The system SHALL write column-seed-derived data to a bind-namespaced SharedMemory key.

#### Scenario: Bind key namespace
- **WHEN** the column-seed sampler finishes initialization
- **THEN** it SHALL write to `__SHARED_MEM_{db}_{table}_bind` (per table)
- **THEN** the value SHALL map each deviceCode to its own row dict `{col_names: [...], row_values: [...], ptag_values: [...], ptag_names: [...]}` — one entry per device, no aggregation
- **THEN** the deviceCode key SHALL be the literal string computed by `calculateDeviceNumber(...)` + `deviceIdentifier(...)` (no hash applied)

#### Scenario: Mixed table key coexistence
- **WHEN** a test plan has both full-row tables and column-bind tables
- **THEN** full-row tables SHALL use `__SHARED_MEM_{db}_{table}` (existing)
- **THEN** column-bind tables SHALL use `__SHARED_MEM_{db}_{table}_bind` (new)
- **THEN** the two namespaces SHALL coexist without collision

### Requirement: Per-deviceCode row dict (one entry per device)

The system SHALL map each device to its own row dict entry keyed by the literal deviceCode string. No `group_id` aggregation, no hash-based bucketing.

#### Scenario: Row count = num_threads (no aggregation)
- **WHEN** `num_threads=T` for a column-bind table
- **THEN** the SetupTG SHALL bake exactly `T` row dict entries (one per device)
- **THEN** the WriteTG ThreadGroup SHALL set `num_threads=T` (not hardcoded to 1)

#### Scenario: Distinct col_names per deviceCode
- **WHEN** two devices share the same row dict entry (legacy many-to-one)
- **THEN** the system SHALL reject this design — every deviceCode MUST have its own entry
- **THEN** the col_names subset for each deviceCode SHALL be computed independently using the SetupTG loop index `t` as offset (`colStart = t * colNumPerTag % dataColumns.size()`)

#### Scenario: No hash dependency
- **WHEN** computing the row dict key
- **THEN** the system SHALL NOT call `Object.hashCode()` or `List.hashCode()` — Groovy's default hash on `[deviceCode]` is degenerate for short numeric-suffixed strings (measured: device_1/device_3 both hash to same group mod 2)
- **THEN** the WriteTG prep SHALL look up the row dict by the literal deviceCode string

### Requirement: Write TG uses ptag-bound column subset

The system SHALL generate a Write TG that writes only the ptag-bound column subset when `col_tag_bind_mode=true`.

#### Scenario: ptag combination maps to row dict by literal deviceCode
- **WHEN** a write iteration computes its deviceCode via `calculateDeviceNumber(threadNum, deviceStart, devicePerThread, 0)` + `deviceIdentifier(...)`
- **THEN** the system SHALL look up `__SHARED_MEM_{db}_{table}_bind[deviceCode]` directly
- **THEN** the system SHALL emit the row dict's `col_names` and `row_values` in the INSERT VALUES position
- **THEN** the system SHALL NOT apply any hash-based grouping

#### Scenario: INSERT column list composition
- **WHEN** the Write TG emits an INSERT for the table
- **THEN** the column list SHALL include `ts`, all `primary_tag` columns, and the ptag-bound subset of `data_col` columns
- **THEN** the column list SHALL NOT include unselected `data_col` columns

#### Scenario: NOT NULL columns must appear in INSERT
- **WHEN** generating the INSERT column list
- **THEN** the system SHALL include any column with `NOT NULL` constraint (whether `ts`, `primary_tag`, or `data_col`)
- **THEN** the system SHALL NOT silently omit NOT NULL columns
- **THEN** per KaiwuDB official docs, partial column INSERT does NOT require column order matching, only value-type alignment

### Requirement: col_tag_bind_mode applies to all 5 modes including schemaless

The system SHALL support `col_tag_bind_mode` for all 5 write modes including `schemaless`.

#### Scenario: SQL mode (single_insert / batch_insert / single_prepared / batch_prepared)
- **WHEN** `col_tag_bind_mode=true` for a SQL mode table
- **THEN** the system SHALL generate inline INSERT with column subset
- **THEN** the underlying `_build_inline_sql_preprocessor_script` SHALL accept the reduced column list

#### Scenario: schemaless mode
- **WHEN** `col_tag_bind_mode=true` for a schemaless mode table
- **THEN** the HTTP/InfluxDB Line protocol body SHALL take partial column values from bind-mode memory seed group
- **THEN** the system SHALL fill only the columns in the current group's `col_names` list
- **THEN** the InfluxDB Line protocol body construction SHALL remain consistent with existing schemaless path

### Requirement: Hash function non-degeneracy (regression test)

The system SHALL provide unit and smoke tests verifying that the hash function used for ptag mapping does not degenerate to a single group.

#### Scenario: Unit test for hash distribution
- **WHEN** the hash function is tested with 16 ptag combinations and `num_threads=4`
- **THEN** the test SHALL assert that ptag combinations map to at least 2 distinct group_ids
- **THEN** the test SHALL fail if hash degenerates to a single group_id

#### Scenario: Smoke test for distinct column subsets
- **WHEN** smoke test runs with `col_tag_bind_mode=true` and multiple ptag combinations
- **THEN** the test SHALL verify that at least 2 distinct INSERT column subsets are observed in the JTL
- **THEN** the test SHALL fail if all inserts have the same column subset
